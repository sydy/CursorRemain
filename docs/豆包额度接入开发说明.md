# 豆包额度接入开发说明

目标：在现有 Cursor 额度监控之外，同时监控「豆包 App 专业版」的订阅额度，并在浮窗里与 Cursor 额度并排展示。

- 调研日期：2026-11-19，对应代码版本 2.1.1（`b51baaf`）
- 状态：方案已定，**尚未开工**；第 2 节的接口验证是阻塞项，未通过前不要写业务代码

## 1. 范围

本期做：

- 豆包账号的添加（内嵌网页登录、手动粘贴 Cookie）
- 定时拉取额度，展示「当前时段（5 小时）/ 近 7 天 / 每月」各档已用百分比
- 浮窗在 Cursor 区块下方增加豆包区块
- 复用现有阈值告警与登录失效通知
- macOS 与 Windows 两端

本期不做：

- 火山方舟 Coding Plan / Agent Plan、方舟按量 API（接口见附录，可后续按同一套 `provider` 机制扩展）
- 豆包账号的云同步（原因见 5.4）
- 豆包账号的用量报表、账号对比、切号
- 菜单栏/托盘图标的变化（圆环仍只反映 Cursor 当前账号）

## 2. 接口

豆包没有公开的额度 API。下面的信息来自 doubao.com 公开前端资源的静态分析，加一次未登录探测。

### 2.1 已确认

请求：

```http
POST https://www.doubao.com/alice/commerce/sale/subscription/quota/summary/
Content-Type: application/json
Origin: https://www.doubao.com
Referer: https://www.doubao.com/chat/
Cookie: <登录后的 .doubao.com Cookie>

{"product_line":"membership"}
```

响应外层为 `{code, data, msg, message, error}`。**HTTP 状态码恒为 200，成功与否只看 `code`**：

| `code` | 含义 | 处理 |
| --- | --- | --- |
| `0` | 成功 | 解析 `data` |
| `710012001` | 登录已过期（`message: "login invalid"`） | 视为登录失效，走现有「Token 需要更新」通知 |
| 其他非 0 | 未知业务错误 | 显示「查询失败」并附 `code`，不要显示 0% |

未登录探测的结果：不带 Cookie、不带任何浏览器签名参数的请求，网关返回的是上面的业务 JSON（`710012001`，响应头 `x-tt-agw-login: 0`），没有被风控拦截。排查问题时可记录响应头 `x-tt-logid`。

`data` 的结构（前端读取到的字段）：

```text
data
├─ member_info                         会员信息（字段名待确认）
├─ window_limit_section
│  ├─ usage_exhausted: bool            整体是否已用尽
│  └─ window_limit_groups[]
│     ├─ feature_group, feature_group_name
│     └─ window_limits[]               ← 额度窗口，见下表
├─ quota_package_section               创作额度包，结构同 window_limit_section
├─ incentive_quota_section             活动赠送额度，结构同上
├─ enterprise_window_limit_section     企业版
└─ enterprise_package_entitlement_groups
```

`window_limits[]` 每一项：

| 字段 | 说明 |
| --- | --- |
| `window_type` | `1` 当前时段（5 小时）、`2` 近 7 天、`4` 每月、`3` 订阅总量（额度包用）、`0` 未知 |
| `used_percent` | 已用百分比，0–100；前端用 `Number()` 解析，**可能是字符串** |
| `less_than_one_percent` | 为 `true` 时页面显示「已用 <1%」 |
| `exhausted` | 该窗口已用尽 |
| `unlimited` | 该窗口暂无限制 |
| `used_amount` / `total_amount` | 字符串，可能缺失；有值时页面显示「已用 x/y」 |
| `end_time` | 窗口结束时间，毫秒时间戳（可能是字符串）；页面只对 5 小时档用它显示「HH:MM 后重置」 |
| `exemption.active` / `exemption.end_time` | 5 小时档的豁免期；生效时该档按「暂无限制」展示，重置时间取豁免结束时间 |

页面文案对应关系：`1` →「当前时段」，`2` →「近 7 天」，`4` →「每月」，额度包 →「创作额度包」。5 小时档没有 `end_time` 时页面显示「开始使用后计时」。

### 2.2 未确认（阻塞项）

1. **带 Cookie 的普通 HTTP 请求能否返回 `code: 0`**。未登录请求没被拦截不代表登录后也不校验签名。
2. **完整的真实响应**。字段名来自压缩后的前端代码，`member_info` 的字段名、是否三档同时返回、`end_time` 在 7 天/每月档是否有值，都需要真实数据确认。前端代码显示个人订阅在一个紧凑面板里只展示「5 小时 + 一个长周期档」，所以不要假定三档齐全。
3. **需要哪些 Cookie**。社区资料称关键是 `sessionid`，未验证。
4. **Cookie 有效期**，以及是否会被服务端滚动刷新。
5. **稳定的用户标识从哪里取**（用于账号去重，见 5.1）。

### 2.3 验证步骤

1. 浏览器登录 doubao.com，开发者工具 Network 里筛选 `quota/summary`。
2. 把响应 JSON 存到 `fixtures/` 下作为夹具原料（金额类数字可改，结构不要动）。
3. 把请求的 Cookie 头的值存到本机文件（不要提交、不要贴到聊天里），用普通 HTTP 请求重放：

```bash
umask 077 && pbpaste > ~/.doubao_cookie   # 先在浏览器里复制 Cookie 头的值
curl -sS -X POST 'https://www.doubao.com/alice/commerce/sale/subscription/quota/summary/' \
  -H 'Content-Type: application/json' \
  -H 'Origin: https://www.doubao.com' \
  -H 'Referer: https://www.doubao.com/chat/' \
  -H "Cookie: $(cat ~/.doubao_cookie)" \
  -d '{"product_line":"membership"}' | python3 -c 'import sys,json; print("code =", json.load(sys.stdin).get("code"))'
rm ~/.doubao_cookie
```

- 输出 `code = 0`：按第 5 节的方案 A 开发。
- 其他结果：改走 5.3 的方案 B，并先重新评估工作量。

## 3. 现有代码里和接入相关的点

逻辑分三层：Rust `core/`（纯逻辑，无网络）、macOS 外壳（`macos/Sources`）、Windows 外壳（`windows/`）。两个外壳的文件基本一一对应，外壳里的每处改动都要写两遍，所以解析和格式化尽量放 core。

| 现状 | 位置 | 对接入的影响 |
| --- | --- | --- |
| 拉取写死 Cursor | macOS `AppStore.fetchOne`；Windows `TrayContext.FetchOne`（`TrayRefresh.cs`） | 需按账号类型分发 |
| 刷新和告警已覆盖所有账号 | `AppStore.refreshAll` / `TrayContext.RefreshAll` | 豆包账号加入后，后台监控和通知基本现成 |
| 账号 id 由 Cursor JWT 推导 | `Token.accountId`、`AppConfig.upsertAccount` | 豆包需要自己的 id 规则和独立的添加入口 |
| 读配置时会规范化 token | `ConfigStore.sanitizeAccount` 调 `Token.normalize` | **会改写 Cookie 串**（去空白、按 JWT 规则加前缀、非 Latin-1 报错），豆包账号必须绕开 |
| token 为空的账号被丢弃 | `sanitizeAccount`、`sync.rs` 的 `merge_snapshots` | 豆包凭据必须放在 `token` 字段里 |
| 当前账号即 Cursor 会话 | `AppConfig.syncLegacyFields` 把当前账号的 token 写入 `sessionToken`，没有当前账号时清空账号列表 | 豆包账号不能成为「当前账号」，相关回退逻辑要逐处改（见 5.4） |
| 云同步是逐字段白名单 | `SyncAccount`、`AccountSync.snapshotPayload`、`sync.rs` 的 `account_from` | 新字段不逐层添加就会丢失 |
| 同步结果整体替换账号列表 | `AccountSync.applySnapshotToConfig`（`cfg.accounts = merged`） | **不参与同步的本地账号会被删掉**，必须显式保留 |
| 快照结构是 Cursor 专用 | `UsageSnapshot`，Grok Bot 额度用一组 `grokBot*` 字段硬加 | 不要再照样加一组豆包字段 |
| 浮窗尺寸固定 | macOS `FlyoutLayout`（500×280）；Windows `FlyoutForm` 里计算 `ClientSize` | 有豆包账号时需要加高 |
| 登录窗口限定 cursor.com | macOS `PasswordLoginController.allowedLoginURL`；Windows `PasswordLoginForm`（WebView2） | 需按平台参数化 |
| 三端共用夹具 | `fixtures/*.json`，由 `core/tests/fixtures.rs`、Swift/C# 的 `FixtureTests` 读取 | 豆包解析沿用同一机制 |

## 4. 数据模型

### 4.1 账号

`Account` 增加 `provider` 字段，取值 `cursor`（默认）或 `doubao`，配置文件里的键为 `provider`。旧配置没有该键时按 `cursor` 处理，无需迁移。

豆包账号的字段约定：

- `id`：`doubao_` 前缀加标识，只含字母数字和下划线（历史文件名会用到它）。标识来源见 5.1。
- `token`：Cookie 头的值（`name=value; name=value`）。落盘时复用 `TokenProtector` 加密。
- `membershipType`：套餐名。优先 `member_info` 里的名字段；免费/个人订阅的 `member_info` 只有布尔位，回退 `current_subscription.display.product_name`（如「个人订阅」），再退 `short_name`（如「免费体验」），都取不到才留空。
- `lastRemaining` / `lastError` / `updatedAt`：沿用，`lastRemaining` 存主百分比。

### 4.2 额度快照

`UsageSnapshot` 增加一个通用的窗口列表，豆包走这个列表，不新增 `doubao*` 字段：

```text
windows: [
  { key: "5h" | "7d" | "1m" | "package" | "incentive",
    label: "当前时段" | "近 7 天" | "每月" | "创作额度包" | "活动赠送额度",
    used_percent: 0–100,
    less_than_one_percent: bool,
    exhausted: bool,
    unlimited: bool,
    used_amount: string?, total_amount: string?,
    reset_at: ISO 时间?,
    count: 整数?   // 仅活动赠送额度：服务端 entitlement_count（条目数）}
]
```

macOS 的 `UsageParser.snapshotJSON` 和 `snapshotFromRust` 要同时带上 `windows`，否则经过 `apply_sand_usage` 往返时会被清空（该函数上方已有注释说明这一点）。

### 4.3 主百分比

告警、历史曲线和账号列表都只认一个 `remaining_percent`，规则如下：

1. 取「近 7 天」和「每月」中 `used_percent` 较大的一档作为主百分比。
2. 这两档都没有时，退到「当前时段」。
3. `window_limit_section.usage_exhausted` 为 `true` 时，剩余直接记 0。
4. 一档都没有（未订阅或结构变化）时，不产出快照，按错误处理并说明原因。
5. 会员三档都没有、但存在创作额度包 / 活动赠送额度时，依次退到 `package`、`incentive` 作为主百分比（免费账号的真实可见额度，不能伪造成 0%）。

「当前时段」不参与告警：它每 5 小时重置一次，接入现有的阈值逻辑会在每个周期反复通知。

## 5. 实现

### 5.1 账号标识与去重（待定）

需要一个重新登录后不变的用户标识，否则同一个豆包账号重新登录会变成两条。候选来源按优先级：

1. 真实响应的 `member_info` 里如果有用户 id，用它。
2. Cookie 里如果有稳定的用户 id 字段，用它。
3. 都没有时：创建账号时生成随机标识，并且只允许从已有账号条目上发起「重新登录」来原地更新 Cookie。

**已确认（2026-11-19）**：真实响应的 `member_info` 没有用户 id，因此在 `uid_tt` 存在时用它；只有 `sessionid` 时按第 3 条生成随机标识，并只允许从已有条目发起「重新登录」原地换 Cookie。

**已确认（2026-11-19，实测）**：免费账号的 `member_info` 只有 4 个布尔位与 `usr_type`，没有套餐名；套餐名在 `current_subscription.display`：`product_name="个人订阅"`、`short_name="免费体验"`。解析按 4.1 的优先级回退，真实响应验证输出 `membership=个人订阅`。

### 5.2 Rust core

新增 `core/src/doubao.rs`，并在 `ffi.rs` 的 `dispatch` 注册：

- `parse_doubao_quota`：入参 `{payload, now}`，出参为与 `parse_usage_summary` 同形的快照 JSON，填好 `used_percent`、`remaining_percent`、`membership_type`、`windows`，其余 Cursor 专属字段给空值。`code` 非 0 时返回 `{error, auth_error}`。
- 数字字段统一用 `jsonutil::as_f64` 读（它已兼容字符串形式的数字），时间戳用 `usage::timestamp_to_iso` 转换。
- 未知的 `window_type` 忽略，不报错。

`sync.rs` 本期不改（见 5.4）。

新增 `fixtures/doubao_quota_cases.json`，至少覆盖：

- 付费账号，三档齐全
- 只有「当前时段 + 一个长周期档」
- `used_percent` 和 `end_time` 为字符串
- `less_than_one_percent`、`exhausted`、`usage_exhausted`
- 5 小时档豁免生效
- 含未知 `window_type`
- 未订阅（没有任何窗口）
- `code: 710012001`

在 `core/tests/fixtures.rs`、Swift `FixtureTests`、C# `FixtureTests` 各加一个读取该夹具的用例。

### 5.3 网络请求

**方案 A（验证通过时采用）**：外壳里新增豆包客户端（macOS `DoubaoClient.swift`，Windows `DoubaoClient.cs`），用普通 HTTP 请求按 2.1 发起，响应交给 `parse_doubao_quota`。重试策略照抄 `CursorClient.requestJSON`（网络错误和 5xx 重试 3 次），但登录失效要从响应体的 `code` 判断，不是 HTTP 状态码。

**方案 B（验证不通过时）**：为每个豆包账号保留一个持久化的网页数据存储，定时在隐藏的 WKWebView / WebView2 里加载 doubao.com 并执行同源 `fetch`，把响应 JSON 传回原生侧。解析和展示部分不变。代价是要常驻或周期性拉起网页内核，内存和稳定性都更差，开工前需重新评估。

两种方案的共同约束：

- 豆包账号的拉取间隔不低于 5 分钟（官方说明额度数据约 5 分钟更新一次），与全局刷新间隔取较大值；手动刷新不受限。
- 只调用这一个只读接口。

### 5.4 配置与云同步

配置读写：

- `ConfigStore.sanitizeAccount` 先读 `provider`，再处理 token；`provider` 不是 `cursor` 时跳过 `Token.normalize` 和从 token 推导 id。
- `ConfigStore.toDictionary` 写出 `provider`。
- 新增独立的添加入口（如 `upsertDoubaoAccount`），不要复用 `upsertAccount`。
- 保证 `activeAccountId` 永远指向 Cursor 账号（没有 Cursor 账号时为空）。菜单里的「切换账号」只列 Cursor 账号。需要改的地方：
  - `AppConfig.activeAccount`：找不到时回退到 `accounts.first`，要改成只在 Cursor 账号里找。
  - `AppConfig.syncLegacyFields`：`activeAccount` 为空时会执行 `accounts = []`。改完上一条后，「只有豆包账号」的配置会走到这里并**清空全部账号**，这个分支必须改成只清 Cursor 相关的旧字段。
  - `ConfigStore.normalizeAccounts`：当前账号的 token 与 `session_token` 不一致时，会用 `session_token` 调 `upsertAccount` 新建账号；回退时取 `accounts[0]`。两处都要限定为 Cursor 账号。
  - `AppConfig.removeAccount`、`AccountSync.applySnapshotToConfig`：回退取「第一个账号」的地方改成取第一个 Cursor 账号。
- 展示哪个豆包账号：配置里加 `active_doubao_account_id`，为空时取第一个豆包账号。
- 以上要有测试：只有豆包账号、只有 Cursor 账号、两者都有，三种配置各做一次读写往返，账号不丢、`session_token` 不被写成 Cookie。

云同步：**本期豆包账号不参与同步**。

- 原因：旧版本客户端不认识 `provider`，同步下来会把豆包账号当成 Cursor 账号，把豆包 Cookie 作为 `WorkosCursorSessionToken` 发给 cursor.com，等于把登录凭据泄露给第三方。
- `AccountSync.snapshotFromConfig`：跳过非 Cursor 账号（连同它们的历史数据）。
- `AccountSync.applySnapshotToConfig`：替换账号列表时，把本地的非 Cursor 账号原样保留。
- `AccountSync.adoptReconciled`：确认本地的非 Cursor 账号不会被当成「同步后多出来的账号」处理。
- 删除豆包账号时不写入 `deletedAccounts`。
- 以上每一条都要有测试，重点是「开启云同步并完成一次同步后，本地豆包账号仍在」。

Windows 的 `AppConfig.cs`、`AccountSync.cs` 做同样的改动。

### 5.5 刷新流程

`AppStore`（Windows 为 `TrayContext`）：

- `fetchOne` 按 `provider` 分发到 `CursorClient` 或豆包客户端。
- 增加一组独立的豆包状态：快照、错误信息、更新时间，由 `active_doubao_account_id` 对应账号的结果填充。现有的 `usage` / `errorMessage` / `updatedAt` 仍只对应 Cursor 当前账号。
- 只有豆包账号、没有 Cursor 账号时，`AppStore.start` 会因为 `sessionToken` 为空而自动弹出设置页，需要改成「一个账号都没有」时才弹。此时 Cursor 区块显示「未添加 Cursor 账号」。
- `AccountValidity.applyEndOverride`（临时账号有效期）只对 Cursor 账号生效。
- 历史记录沿用 `UsageHistory.append`，`remaining` 写主百分比，`auto` / `api` 留空。

告警沿用 `AlertLogic.evaluate`，传入主百分比。耗尽风险预警依赖周期起止时间，豆包暂时拿不到，本期对豆包账号关闭。

### 5.6 登录与添加账号

macOS：把 `PasswordLoginController` 的起始地址、域名白名单、成功判定参数化，或另建一个结构相同的豆包登录控制器。

- 打开 `https://www.doubao.com/`，用户自行扫码或验证码登录，不做自动填充。
- 每 1.5 秒从 `httpCookieStore` 读取域名以 `doubao.com` 结尾的 Cookie，拼成请求头的值。
- 成功判定：用拼出的 Cookie 调一次额度接口，`code` 不是 `710012001` 即视为已登录。不要只凭某个 Cookie 是否存在来判断。
- 每个账号使用独立的网页数据存储，重新登录时可以复用上次的会话。现有的 `LoginProfileStore` 用邮箱和 Cursor token 生成索引键，豆包账号改用账号 id 作键。

Windows：`PasswordLoginForm` 已基于 WebView2，按同样方式参数化。

设置页的账号区增加「添加豆包账号」，包含网页登录和粘贴 Cookie 两种方式；账号列表里用标记区分豆包账号。浏览器 Cookie 导入（`SessionImporter`）目前写死了 Cursor 的 Cookie 名和域名，本期不扩展。

### 5.7 界面

浮窗：

- 没有豆包账号时保持现状。
- 有豆包账号时，在 Cursor 区块下方增加豆包区块：标题行（账号名、套餐、更新时间），下面每个窗口一行，复用现有的 `meterRow` 样式。
- 行内文案沿用网页的规则：`unlimited` 显示「暂无限制」；`exhausted` 显示「已用完」；`less_than_one_percent` 显示「已用 <1%」；有 `used_amount` / `total_amount` 时显示「已用 x/y」。
- 「当前时段」行在有 `reset_at` 时显示重置倒计时，没有时显示「开始使用后计时」。
- 出错时区块内显示错误文案；登录失效时提供「重新登录」入口。

## 7. 风险

- **私有接口**：没有官方支持，字段和风控策略可能随网页发版变化。解析必须容错，失败时明确显示「查询失败」。
- **凭据敏感**：豆包 Cookie 等同于完整登录态，可访问聊天记录等全部数据。除本机加密落盘外不外传，日志里不得出现 Cookie 内容。
- **账号风控**：以固定间隔从非浏览器环境请求，存在被判定异常的可能。控制频率，只调一个只读接口。
- **服务条款**：这是对私有接口的自动化访问，是否对外发布该功能需要自行判断。
- **有效期未知**：如果 Cookie 很快过期，体验会明显差于 Cursor Token，届时考虑方案 B 或利用持久化网页会话静默续期。

## 附录：其他豆包相关额度的接口

本期不做，记录备查。以下均来自公开资料，未用真实账号验证。

火山方舟 Coding Plan：

- `POST https://open.volcengineapi.com/?Action=GetCodingPlanUsage&Region=cn-beijing&Version=2024-01-01`，请求体 `{}`
- 需要火山引擎 AK/SK 做 V4 签名（service `ark`、region `cn-beijing`），`ark-` 开头的 API Key 不可用；子账号需要 `ark:GetCodingPlanUsage` 权限
- 返回 `Result.QuotaUsage[]`，每项 `Level`（`session` / `weekly` / `monthly`）、`Percent`、`ResetTimestamp`（秒，≤0 表示无）
- `Percent` 的量纲（0–100 还是 0–1）资料不一致，官方 CLI 文档写的是 0–100
- Agent Plan 的接口名有 `GetAFPUsage` 和 `GetAgentPlanAFPUsage` 两种说法
- 参考：[ark-cli 套餐用量说明](https://github.com/volcengine/ark-cli/blob/main/skills/arkcli-usage/references/arkcli-usage-plan.md)、[CodexBar 的实现讨论](https://github.com/steipete/CodexBar/issues/1724)

方舟按量 API：

- 单模型免费推理额度：[`GetModelActivation`](https://ark.volcengine.com/region:cn-beijing/docs/get-model-activation-api)，请求体带 `WithFreeUsage: true`
- 账户余额：billing 服务的 `QueryBalanceAcct`（`Version=2022-01-01`）
- 同样是 AK/SK 签名

豆包订阅相关的其他网页接口（同在 `/alice/commerce/sale/` 下，均为 POST，参数未分析）：`subscription/status/`、`subscription/overview/`、`subscription/detail/`、`subscription/quota_balance/detail/`、`entitlement/usage_detail/`。如果 `quota/summary` 拿不到套餐名或到期时间，可以从这几个里找。
